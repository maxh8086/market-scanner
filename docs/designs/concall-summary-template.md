# Concall summary template (local LLM)

Status: draft, awaiting approval. No code changed yet. Extends `docs/designs/concall-pipeline.md`.
Date: 2026-11-09.

## Decisions this template follows

1. Fundamentals come from the collector into the database, and the UI reads only from the database. The existing screener.in path (`scanner/screener.py`, `scanner/fundamentals.py`) stays as it is.
2. Concall summaries are generated by our own local LLM, with our own prompt and template. No site text is copied.
3. Inputs come from the database and local files. Outputs are written back to the database.
4. **No verdicts from the system or the LLM.** The system reports what was said, shows the evidence, and explains what each indicator means. Every buy, add, hold, trim, sell, or rebalance decision is the user's. The output never contains a recommendation, a label such as "bullish" or "cheap", or a price target.

## Inputs (database and files only)

| Input | Source |
|---|---|
| Transcript or presentation text, with page numbers | `concall_events.text` (from `concall-pipeline.md`) |
| Meeting date, meeting type, host names | `concall_events` columns |
| Company name, symbol | `symbol_listing` |
| Previous call summary (optional, for "changed since last call") | `concall_summaries`, previous quarter |
| Annual report text (later version only) | Local file, path stored in the database |

The model never fetches anything. It reads only the passages it is given.

## Outputs (database)

New table `concall_summaries`, one row per `(symbol, seq_id, kind)`:

- `kind`: `overview`, `summary`, `qa`, `annual_report`. The transcript tab shows raw text and does not use the LLM.
- `body`: JSON matching the schema below.
- `prompt_version`, `model_tag`, `source_hash`, `created_at`, `status` (`ok` or `failed`), `check_report` (which checks passed, which items were flagged).

A row is written only when the required checks pass. A failed run leaves the previous `ok` row in place, so the UI never shows partial output.

## Model routing

The local model is chosen by tokenfrugal (builder or thinker role). This template does not name a model, per `CLAUDE.md`. Work goes through `tokenfrugal.dispatch_task`. Context is 16k to 32k tokens, so long transcripts are chunked.

## Reading guide (fixed text, written by us, shown in the UI)

The LLM does not write this section. It is a fixed glossary. The UI shows the entry beside any indicator that appears in a summary. Each entry has four parts: what it measures, how to read a rise or fall in plain words, what would change the reading, and where the number comes from. None of the entries says what to do.

| Indicator | What it measures | Reading a rise or fall | What would change the reading | Source |
|---|---|---|---|---|
| Guidance direction | Management's own statement about the next period | A stated raise or cut tells you what management expects. It is not a result. | The next call, or the reported figures | Concall text |
| Revenue and profit growth | Change in reported sales and profit against the same period last year | Growth with falling margin means costs or prices moved against the company, if management says so. | Restated figures, one-time items | Results filing |
| Operating margin | Operating profit as a share of sales | A fall with flat sales points to cost pressure. Check what management gave as the reason. | Input cost changes, mix changes | Results filing |
| Order backlog | Contracts won and not yet executed | A rising backlog means more contracted future revenue, not profit. Check execution timelines and cancellations. | Execution delays, cancellations, scope changes | Announcements, concall |
| Capex | Money spent on new assets | Rising capex usually means future capacity. The return depends on commissioning dates. | Delays, cost overruns | Concall, annual report |
| Debt-to-equity | Borrowing against the company's own capital | A rise means more borrowing relative to equity. Check why the borrowing rose. | Repayments, new equity | Balance sheet |
| Promoter pledge | Share of promoter holding used as security for loans | A rise is a flag to check, not a conclusion. | Pledge release, invocation | Shareholding filing |
| Auditor change or resignation | Change of the company's auditor | Shown as a flag. The filing gives the stated reason. | Stated reason, follow-up filings | Announcements |
| Credit rating action | Change in a rating agency's rating | A downgrade signals the agency's view of repayment risk. | Re-rating | Announcements |

Entries are added only after review. An indicator that is not in this table is shown with the text "no reading guide yet" and no reading.

## Rules for the model

These rules are written into every prompt.

1. Use only the text in the input. If the input does not say something, write `not stated`.
2. Every item has a `quote`, copied exactly from a passage, and a `cite` (the page id of that passage). The paraphrase goes in `text`.
3. Every item has a `qualifiers` field. Record every condition, hedge, or limit that management attached to a statement: "expect", "may", "subject to", "one-time", "excluding", "on a reported basis", "for the India business only". Use `not stated` if there are none. Qualifiers are the nuance that most summaries lose.
4. Report what management or analysts said. Do not give an opinion, forecast, verdict, or target.
5. Copy figures exactly, with unit and period as written. Do not round or convert units.
6. Attribute each statement: "Management said", "An analyst asked", or the analyst firm if the input gives it.
7. Plain English. Short items. No adjectives that judge the company.

## How nuance and detail are caught with a local model

A 4B-class model misses detail in long input and tends to smooth over qualifiers. The design does not rely on one prompt. It uses these layers, each one a separate check:

1. **Narrow passes.** One topic per call (guidance, margins, capex, risks, Q&A themes), not one large summary. Smaller tasks keep more detail.
2. **Quote first.** The model must copy the supporting sentence before it paraphrases. Application code then checks that the quote appears in the passage word for word. A paraphrase with no matching quote is rejected. This is the strongest check against invented content.
3. **Figure check.** Every number in the output must appear in the input text, as a string match. (`enrich.py` already cross-checks regex-extracted rupee values against LLM values using `llm.cross_check`. The same pattern applies here.)
4. **Direction check.** Application code looks for direction words near a figure ("fell", "declined", "lower", "improved", "higher") and compares them with the sign of the change the model reports. A mismatch is flagged for the user. The check cannot judge meaning, so it only flags.
5. **Qualifier check.** Each output item with a hedge word in its quote must have a non-empty `qualifiers` field. A missing qualifier is flagged.
6. **Thinker cross-check.** A second, separate pass asks: does this quote support this text? Answers are `yes`, `partial`, or `no`. `partial` and `no` are shown to the user as "check this".
7. **Gold set.** You label 3 to 5 concalls by hand: the key figures, guidance, and qualifiers. We measure how many the pipeline captures and whether any figure is invented. The thresholds are set with you before the prompt is released.
8. **Show the evidence.** Every item in the UI shows its quote and page. The user checks the source. The system does not interpret the item for them.

Limit: layers 1 to 6 catch invented figures, wrong quotes, and dropped qualifiers reliably. They catch a misread meaning only partly, through the thinker check and the gold set. Layer 8 is the final safeguard, and the design depends on it.

## Prompt skeleton (per topic)

```
You extract one topic from an earnings call for an Indian listed company.
Use only the passages below. Do not use outside knowledge.
For each item: copy the supporting sentence exactly as "quote", then write a short "text".
Record every hedge or condition in "qualifiers". Write "not stated" if there is none.
If the passages do not cover the topic, return an empty list.
Do not give any opinion, forecast, or verdict.
Return only JSON matching the schema below.

Company: {company}. Call date: {call_date}. Period: {period}. Topic: {topic}.
Previous call summary (may be empty): {previous_summary}

Schema:
{schema_for_topic}

Passages:
{passages_with_ids}
```

## Chunking

1. Split the transcript by page. Group pages into chunks of about 6,000 to 8,000 tokens.
2. For each chunk and each topic, ask for notes in the item format above.
3. Merge the notes into the final JSON in a second pass. The second pass sees notes only, not full text, and it may not add a figure or quote that is absent from the notes.

## Checks (application code, not the model)

Run after every model reply. A failure means one retry, then `status = failed` if it fails again.

Required, the row is rejected if any fails:

1. The reply parses as JSON and matches the schema for that `kind`.
2. Every `cite` exists in the passage ids that were sent.
3. Every `quote` appears word for word in the cited passage.
4. Every number in `text` appears in the input text.
5. No banned words in `text`: buy, sell, hold, add, trim, rebalance, target, recommend, bullish, bearish, cheap, expensive. (Quotes are exempt, because management may use these words.)

Flagged, the row is stored and the item is marked in the UI:

6. Direction mismatch (layer 4).
7. Missing qualifier on a hedged quote (layer 5).
8. Thinker cross-check result `partial` or `no` (layer 6).

## Versioning

- `prompt_version` is a string such as `concall-summary-v1`. Changing the template changes this value.
- `source_hash` is a hash of the input text. If the input and version are unchanged, the row is not regenerated.

## Open risks

- **Template matches our style, not theirs.** I have not copied concall.in's wording or layout. The tone will be tuned against a sample you provide.
- **Transcript availability.** Not every concall has a transcript on the exchange. For those, the summary comes from the presentation only, and is labelled that way.
- **Model limits.** Layers 1 to 6 are the design's answer to the limits of a local 4B-class model. The gold set (layer 7) is the only measure of how well they work. Until it runs, summaries are not trusted for decisions.
